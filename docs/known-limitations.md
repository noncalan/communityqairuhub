# Known limitations

These are current repository limitations, not a speculative roadmap. A suggested next step is guidance, not evidence that the work is scheduled.

| Current limitation | Impact | Suggested next step |
| --- | --- | --- |
| No university-domain or student-status verification | Any email accepted by hosted Supabase Auth may register; “authenticated” does not mean “verified QAIRU student.” | Add an explicit verified-student state and enforce it in application checks and RLS before expanding access. |
| `/opportunities` is a live placeholder | Live users cannot browse verified internships, grants, or competitions; demo listings are illustrative only. | Design a trusted publisher, schema, review workflow, and live directory before enabling listings. |
| `/admin` has only a role gate and placeholder | Admin authorization is testable, but there is no moderation or operational tooling. | Implement separate admin data/actions with independent authorization tests; do not rely on hiding UI. |
| No reporting/moderation workflow | Users cannot report content/accounts, and staff cannot record actions such as hide/warn/block. | Add report entities, queue/actions, decision audit log, user feedback, and abuse ownership. |
| No `/help`, privacy, terms, or user-facing rules | Users lack an in-product support/report channel and clear data/use guidance. | Add reviewed help, community rules, privacy, terms, and contact pages. |
| Live global search only navigates to sections | `Ctrl/Cmd+K` does not search live entities. Directory filters search only their already-fetched bounded result set. | Add a permission-aware search API/index and entity results, or describe the palette as navigation only. |
| Profile lifecycle is incomplete | No managed avatar upload, social links, languages, weekly availability, account deletion, or automatic project/event history. Settings also do not edit the new academic direction/desired role/contribution fields. | Define the profile contract, add safe storage if needed, extend the atomic RPC/UI, and define owned-entity deletion/retention. |
| Project management is creation/application-focused | There is no project edit UI, role management UI, repository URL, goals, update history, rejection reason, or application-withdraw UI. Project pages require authentication. | Add owner/editor screens and history fields with RLS/tests; decide whether a narrow public showcase is intended. |
| Community management is incomplete | Generic communities can be created/joined and have posts, but the inspected UI has no generic edit, moderator tooling, charter, or lifecycle workflow. | Add owner/moderator management and moderation actions using existing roles as the authorization base. |
| Event lifecycle is incomplete | No event edit UI, waitlist, reminders, check-in, calendar export, or post-event outcome. | Add lifecycle schema/actions and notification delivery with capacity/concurrency tests. |
| Home is a social feed, not an automatic activity timeline | Project/team/event changes do not generate durable activity/update entries. | Add an activity/update model and trigger or service-owned generation rules if this remains a product requirement. |
| Telegram is only a club handoff prototype | There is no QAIRU profile↔Telegram link, group membership/admin verification, reminders, quick actions, or personal notification delivery. | Add an explicit identity-link/consent model and verify bot permissions before claiming deeper integration. |
| Telegram webhook rate limiting is per process | Requests distributed across Vercel instances do not share counters; restarts reset state. | Move abuse state to a shared durable store or edge/firewall rate limit if traffic requires it. |
| Storage-backed uploads are disabled | Resource files and message attachments cannot be uploaded; club logos must be external trusted HTTPS URLs. | Add private buckets, ownership paths, MIME/size allowlists, signed reads, cleanup, and cross-account Storage tests before enabling UI. |
| Message privacy controls are minimal | Any discoverable profile can be messaged; there is no block, request inbox, spam handling, or attachment support. | Add block/request policies and abuse controls at the database and UI layers. |
| Notification delivery is in-app only | No email/Telegram delivery, preferences, reminders, or invitation notification type exists. | Add consented channels/preferences and idempotent delivery jobs after identity linking. |
| Core API uses a privileged Supabase key | RLS is bypassed after Bearer authentication; a leaked key or allowlist bug has broad impact. | Keep both credentials server-only, rotate them, restrict callers, monitor use, and add deployed HTTP integration tests. |
| Core API is intentionally narrow | No DELETE, Auth-user creation, roles/technologies in project creation, or new onboarding fields in the user mutation allowlist. | Extend only with explicit contracts, field projections, validation, ownership side effects, and tests. |
| Vercel Web Analytics is not integrated | `@vercel/analytics` is installed but no Analytics component is rendered, so package presence alone does not provide page analytics. | Either render and verify the approved Analytics integration or remove the unused dependency. |
| Automated coverage is not end to end | Unit and pgTAP coverage is strong, but email, browser, Realtime, Telegram, Core HTTP, deployment, accessibility, and mobile flows remain manual. | Add browser E2E and isolated integration environments; retain manual two-account checks for external delivery. |
| pgTAP depends on fixed development account UUIDs | The SQL suites cannot run safely against arbitrary databases and must never run in production. | Keep a disposable seeded test project/local stack or make fixture provisioning self-contained. |
| Node tests emit module-type warnings | Tests pass, but Node reparses TypeScript modules because `package.json` has no `type`. | Evaluate adding `"type": "module"` separately and run the full build/test suite because it can change module semantics. |
| Local Auth origins are inconsistent | `supabase/config.toml` uses `127.0.0.1:3000`; `.env.example` and the standard app command use `localhost:3010`. Confirmation/recovery redirects can fail until aligned. | Choose one local origin and update the config, environment, and run command together. |
| Hosted Auth/advisor state is not current evidence | The August audit recorded leaked-password protection disabled, but the repository cannot show whether it was later enabled; SMTP/CAPTCHA/redirect settings are also external. | Re-run hosted Auth checks and Supabase advisors before broader access, then record a dated result. |
| Custom-domain/DNS state is unverified | Older docs name `community.qairuhub.com`, but no DNS configuration or current domain attachment is committed. No repository evidence proves a current DNS problem or successful setup. | Verify the Vercel domain attachment, DNS records, TLS, canonical site URL, and Supabase redirect allowlist in the live control planes. |
| Local deployment links are prototype-named | Ignored Vercel metadata and the linked Supabase project currently use prototype-oriented names, which raises environment-selection risk. | Confirm and label Preview/Production projects before deployment; never infer production from the local link alone. |

## Historical warnings

Files under `docs/audits/` and `docs/product/mvp-status.md` are dated snapshots. In particular, the 2026-09-07 MVP document predates `/find`, and the 2026-08-14 security audit predates the Core API's privileged server client. Use this document and the other top-level current-system documents for present-state claims, while retaining the audits as evidence of what was checked at that time.
